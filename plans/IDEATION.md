# IDEATION — Extracting the Juice from "Towards a Double Operadic Theory of Systems"
[restored verbatim 2026-09-16 · superseded where marked by CONSENSUS.md R1–R6 and ADVERSARIAL.md]

**Source, tunnel-vision:** Libkind & Myers, arXiv:2505.18329v2 (80 pp). No outside literature
except named competitors (AST-aware compression, Headroom) as *targets*, not sources.

**Mission:** From this one paper, derive a research program + eventual paper that can
(1) map the wiring of any large production codebase, (2) find symmetries à la Noether with
conserved quantities, (3) use the double operadic lens to beat AST-aware token compression.

---

## 1. What the paper actually gives us (the asset inventory)

**A1 — The ontology (Fig. 1).** Four entity kinds and nothing else: `system ⊸ interface`,
`interaction : interface ↛ interface`, `system map` (vertical), `interaction/interface maps`.
Everything a "systems theory" is, is an answer to six questions (Informal Def 1.1). This is a
*schema for describing any composite thing* — including a codebase — with a tiny typed vocabulary.

**A2 — Interfaces as the whole story.** Axiom: all interaction happens through the interface;
the environment needs to know nothing else. This is the *license for compression*: the token-cost
of a subsystem, seen from outside, is the token-cost of its interface + black-boxed behavior,
NOT of its implementation.

**A3 — Module of systems.** Systems + maps form a symmetric monoidal loose right *module* over a
double category of interfaces + interactions. The key structural move: composition patterns
(interactions) are first-class citizens that *act* on systems. Codebase reading: the dependency
/call/data-flow structure is not metadata about the code — it is an algebraic object that acts
on module-summaries.

**A4 — Three doctrines of composition** (§5–7): (a) **lens composition** (Moore machines, ODEs,
POMDPs) — directed, state+update; (b) **port-plugging / pushout** (Petri nets, undirected wiring
diagrams) — gluing along shared ports; (c) **variable sharing** (Willems behavioral, spans) —
composition by constraining shared variables. Codebase reading: real systems mix all three —
function calls are lens-like (directed request/response), pub/sub and shared DBs are
variable-sharing, linking/imports are port-plugging. A codebase wiring map should *type each edge
by its doctrine*. [SUPERSEDED by R1: cospan is the single formal spine; others are annotations.]

**A5 — Maps between systems** (the double direction — the paper's headline addition):
refinement, coarse-graining, simulation, trajectories, steady states, Lyapunov functions.
Codebase reading: a **language port is a system map** (Java-repo → Go-repo) that lives over an
interface map; a refactor is an interaction-preserving map; a mock/stub is a coarse-graining;
tests are behavior maps (trajectories into the system). Migration correctness = the square
commutes.

**A6 — Pseudo-functoriality ⇒ black-boxing recipes.** The constructions are pseudo-functorial,
giving compositionality theorems: behavior of the whole computable from behaviors of parts +
pattern. Codebase reading: summarize leaves, compose summaries along the wiring — a *provably
structured* alternative to "stuff files into context."

**A7 — Wiring diagrams are FREE processes (§8).** Diagrammatic interaction patterns are *free*
objects in the relevant doctrines. Free = generated by a small set of generators with no
relations beyond the forced ones. This is the deepest compression lever: if interaction patterns
are free, then every wiring has a canonical *minimal presentation* — generators + counts —
and repeated patterns (the same wiring shape instantiated 400×) cost one generator + 400 cheap
instantiations, not 400 spelled-out subgraphs. [SUPERSEDED by R3/GA4: freeness gives lossless
factoring, NOT canonical minimal presentations; minimality is engineering.]

## 2. The three target capabilities, derived from the assets

### T1 — "Map the wiring" (A1+A3+A4)
A codebase → a **module of systems**: nodes are code units summarized *at their interface*
(exports, signatures, contracts, effects); edges are interactions *typed by doctrine* (lens /
port-plug / variable-share); the whole is a labelled double category instance. Deliverable form:
a `WiringMap` = (interface catalog, interaction pattern, system-card per node). This is exactly
the "plumbing understanding" that large orgs lack.

### T2 — Noether: symmetries ⇒ conserved quantities (A5+A6) [SUPERSEDED by R2: T2a/T2b/T2c split]
Noether's schema: every symmetry of the action yields a conservation law. Transplant:
- **Symmetry** = automorphism of the wiring (interaction-pattern symmetry: subsystems that are
  interchangeable because they occupy isomorphic positions with isomorphic interfaces), or a
  natural family of system maps (e.g., "rename/relocate without interface change").
- **Action** = the composite black-boxed behavior (A6's compositionality).
- **Conserved quantity** = whatever the black-boxing functor sends symmetric configurations to
  the same value on: API contracts, data-flow balance (Petri-net token conservation is literal
  Noether here [SUPERSEDED: false as support, see CONSENSUS R2]), resource ownership, protocol state.
Practical yield: (i) **orbit compression** — send one representative per symmetry orbit to the
LLM plus the group action ("these 37 services are the same shape; here is the shape once");
(ii) **migration invariants** — the conserved quantities are exactly what a port/refactor must
preserve, giving a checklist that is *derived*, not hand-written.

### T3 — Beat AST-aware compression (A2+A7+T2)
AST-aware compression exploits *intra-file syntactic* redundancy. The operadic lens exploits
**cross-file structural** redundancy, which dominates in production codebases (frameworks force
repeated wiring shapes). Compression pipeline hypothesis:
1. Interface-only projection (A2): drop implementations when the task allows — bounded by
   black-box sufficiency.
2. Free-pattern factoring (A7): wiring → generators + instantiation table (a "pattern
   dictionary" with algebraic guarantees instead of ad-hoc dedup).
3. Orbit folding (T2): quotient by wiring symmetries; ship representative + action.
4. Doctrine-aware elision: lens edges admit interface-behavior summaries; variable-sharing
   edges need the shared-variable schema only; port-plugging needs port types only.
Token accounting: cost(codebase-context) ≈ cost(generators) + cost(interface catalog) +
cost(orbit reps) + O(instantiation table) — versus AST compression's ≈ Σ_files cost(compressed
file). On repetitive million-file codebases the former should win asymptotically. [SUPERSEDED
by R4: restated as pre-registered CR@F95 Pareto claim.] That is the falsifiable claim of the
eventual paper.

### The hard problem (million-file translation) as the capstone
Translation = construct a system map into a new module of systems over the *same* interface
double category. Because of A6, correctness decomposes: translate leaves, verify each
composition square commutes (tests at interfaces = OC-style consistency gates: the translated
composite must agree with the composite of translations). Context needed per step is bounded by
the interface + local wiring — never the whole codebase. Compression (T3) is what makes each
step affordable; the wiring map (T1) is what sequences the steps; the invariants (T2) are what
"correct" means.

## 3. Mental-model-only leverage (no code needed)
- The six questions of Informal Def 1.1 as an *intake protocol* for any architecture/system.
- "Interface first, interaction second, internals last" as a context-construction discipline
  for prompting about code.
- Doctrine-typing of edges as a whiteboard practice (which of the 3 composition modes is this?).
- Noether-questioning: "what symmetry does this design have, and what does it conserve?" as a
  design-review lens.
- The meta-suite analogy: as meta-prompting solved the *category of prompts*, DOTS solves the
  *category of systems theories* — a meta-theory. The suite-building move to imitate: turn each
  doctrine into a skill-like reusable instrument.
